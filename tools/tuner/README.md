# 인프라 최적값 탐색기

부하 시험 점수를 최대로 만드는 인프라 구성을 **측정 → 모델 → 탐색** 으로 구한다.
앱이 바뀌어도(요청당 비용이 달라짐) 트래픽이 바뀌어도(도착률이 달라짐) 같은 절차를 다시 돌리면 된다.

## 왜 이런 구조인가

점수는 두 항목이 서로를 잡아먹는다.

- **성능** — 요청의 SLA(200ms) 통과율. 노드를 늘리면 오른다.
- **비용** — 노드 수. 노드를 늘리면 깎인다. 0.5대당 1점.

그래서 "노드를 늘린다/줄인다" 로는 답이 안 나오고, **어느 지점에서 교환이 이득인지**를 계산해야 한다.
계산에 필요한 건 딱 두 가지다.

```
요청 지연  ≈  F  +  d / (1 - ρ)
    F : 고정 오버헤드 (DB·네트워크·직렬화)
    d : 그 요청의 CPU 작업량 (분포)
    ρ : CPU 이용률 = 총수요 / 실효용량
```

`F` 와 `d` 는 앱에서 실측하고, `ρ` 는 노드 수의 함수다. `d` 를 **분포 전체**로 다루는 게 핵심인데,
이 앱은 10% 의 요청을 4~8배 무겁게 만들도록 설계돼 있어서 평균만 보면 SLA 통과율을 못 맞춘다.

### 측정에 앱의 협조가 필요 없다

`F` 와 `d` 는 **커널이 세는 CPU 카운터**와 **클라이언트가 재는 지연**만으로 분리된다.

```
파드를 1개로 줄이고 동시성 1 로 N 번 때린다  →  큐 대기가 없으니  L_i = F + d_i
d_mean = Δ(container_cpu_usage_seconds) / N      ← kubelet 이 노출하는 누적 CPU
F      = mean(L) - d_mean
d_i    = L_i - F                                  ← 무거운 꼬리까지 그대로
```

앱에 프로파일링 엔드포인트도, 작업량 조절 변수도 요구하지 않는다.
**대회에서 바이너리만 주어져도 그대로 쓸 수 있다.**

**검증 결과** — 이 연습용 앱에는 마침 `LOAD_MULT` 라는 작업량 변수가 있어서,
그걸 꺼서 구한 값과 커널 카운터로 구한 값을 대조했다.

| | F (고정비) | d (요청당 CPU) |
|---|---|---|
| `LOAD_MULT` 조작 (앱 협조 필요) | 12.72 ms | — |
| 커널 CPU 카운터 (앱 협조 불필요) | **12.95 ms** | 9.22 ms |

원리가 완전히 다른 두 방법이 `F` 를 **1.8% 오차로 일치**시켰다. 대회용 경로는 커널 카운터 쪽이다.

측정 시 주의 두 가지 (둘 다 실측으로 확인):
- **파드가 1개로 정리될 때까지 기다려야 한다.** 축소 직후엔 종료 중인 파드가 목록에 남아
  엉뚱한 파드의 CPU 를 읽는다 → CPU 가 0 에 가깝게 나온다.
- **프로브를 30초 이상으로 잡아야 한다.** cAdvisor 가 10~15초 주기로 갱신되므로
  짧은 프로브는 CPU 를 과소 측정한다 (1.4초 프로브에서 실제의 23% 만 잡혔다).

## 사용법

```bash
./profile.sh user            # 앱마다 1회. F 와 d 분포를 실측 → profile-user.json
./profile.sh product
./profile.sh stress

python3 calibrate.py         # 과거 회차 결과로 실효용량 계수 보정 → calibration.json

./solve.py --traffic '{"user":44,"product":48,"stress":2.5}'   # 후보 노드 수 계산

./sweep.sh 1 3 4 5           # 후보를 실제로 돌려 확정 (결과는 observations.json 에 누적)

./apply.sh 3                 # 고른 값을 고정
./verify.sh 1 6              # 확인 회차
```

## 각 스크립트

| 파일 | 하는 일 |
|---|---|
| `lib.sh` | SSM 으로 bastion 에서 kubectl 실행, 채점 서버 제어 |
| `profile.sh` | 파드 1개 + 동시성 1 + 커널 CPU 카운터로 **고정비 F** 와 **CPU 작업 분포 d** 를 분리 측정 (앱 손잡이 불필요) |
| `solve.py` | 실측 `d` 표본을 이용률만큼 늘려 SLA 통과율을 계산하고, 노드 수별 점수를 전수 비교 |
| `calibrate.py` | 실제 회차 결과로 **실효용량 계수**를 역산. 모델의 가정 오차를 현실로 흡수 |
| `apply.sh` | `minDomains`(하한) + NodePool `limits.cpu`(상한) 로 노드 수를 고정 |
| `sweep.sh` | 후보를 실제로 돌려 최고 점수를 확정하고 관측을 누적 |
| `verify.sh` | 채점 회차 1회 실행 + 점수 출력 |

## 측정으로 확인된 것

### 1. 지연의 정체는 앱의 CPU 작업이다
DB·네트워크·ALB 를 전부 합친 고정비는 **13ms** 뿐이고 나머지가 전부 CPU 다.
(대조 검증: `LOAD_MULT` 0.3 → 0.01 로 CPU 작업만 끄자 POST p50 **83ms → 21ms**,
p90 **165ms → 38ms**. 커널 카운터로 구한 F 와 일치한다.)

### 2. 실효 CPU 는 원시 vCPU 의 31% 다
보정 결과 공유 풀 `usable = 0.31`, stress 전용 풀 `0.72`.
여러 파드가 동시에 64KB 버퍼를 해싱하면 캐시·메모리 대역폭 경쟁으로 코어당 처리량이 떨어진다.
**설정으로 없앨 수 없는 손실이라 모델이 흡수한다.** ALB 는 이미 `least_outstanding_requests` 라
큐 분산 손실은 해당 없음.

### 3. `minDomains` 는 하한, NodePool `limits.cpu` 는 상한 — 둘 다 필요하다
- `minDomains` 없으면: 스케줄 가능한 노드가 1대일 때 skew 가 항상 0 이라 파드가 Pending 되지 않는다
  → Karpenter 가 안 깨어난다 → 한 노드에 파드가 쌓인다 (실측 x0.5 37.0점)
- `limits.cpu` 없으면: HPA 가 파드를 늘리는 만큼 노드가 계속 붙는다 (실측 9대, 비용 0/12)

### 4. 최적 노드 수는 "성능 티어를 갓 넘기는 최소값" 이다

x1.0 에서 공유 노드 수를 바꿔가며 실측한 결과:

| 공유노드 | 총 | 점수 | avg_ec2 | user 성능 | up50 |
|---|---|---|---|---|---|
| 2 | 3 | 34.0 | 3.00 | 73.3% | 160ms |
| **3** | **4** | **35.0** | 3.83 | 91.2% | 110ms |
| 4 | 5 | 30.5 | 6.00 | 97.2% | 92ms |
| 5 | 6 | 28.5 | 6.67 | 98.8% | 78ms |

**비용은 0.5대당 1점, 성능은 티어당 0.5점**이라 비용 쪽이 두 배 가파르다.
그래서 성능을 최대화하는 게 아니라 **성능 티어(90%)를 갓 넘기는 최소 노드**가 최적이다.
노드를 4대 이상으로 늘리면 성능은 오르지만 이미 만점 구간이라 비용만 잃는다.

주의: 위 표의 4·5·2 행은 채점기 `ec2_offset` 이 어긋난 구간이라 `avg_ec2` 를 +1 정정한 값이다.
과제와 무관한 인스턴스가 계정에 있으면 오프셋을 반드시 맞춰야 비용 점수가 정확하다.

### 5. 노드 수가 성능을 지배한다 (다른 건 거의 무관)
x1.0 에서 아래는 전부 **지연에 영향이 없었다**:
DB `max_connections`(27→150), 파드 수(20→6), maxPods(17→110), `requests.cpu`(70m→140m).
반면 노드 9대에서는 up50 이 165ms → **63ms**, user 성능 74% → 92% 로 바뀌었다.

## 앱·트래픽이 바뀌면

- **앱 변경** → `./profile.sh <app>` 다시. `F`/`d` 가 갱신된다. 새 앱이면 `profile.sh` 의 `case` 에
  요청 본문 한 줄만 추가한다. 앱 내부를 알 필요도, 소스가 있을 필요도 없다.
- **트래픽 변경** → `solve.py --traffic` 의 숫자만 바꾼다.
- **인스턴스 타입 변경** → `solve.py --vcpu` 를 바꾸고 `calibrate.py` 를 다시 돌린다.
- 어느 쪽이든 `sweep.sh` 로 실측 확정하는 절차는 동일하다.
